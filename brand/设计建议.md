# OnlyRead Logo 设计建议

> 面向：OnlyRead v0.1.0（Electron + React 的跨平台本地文件阅读器）
> 本文基于仓库现状写成，不是通用 logo 教程。文中引用的文件路径均可直接打开核对。
>
> **命名变更**：产品原名 `OnlyRead`，因下述商标撞车风险已改名为 `OnlyRead`。
> 本文已按新名整体更新；第 1.4 / 1.5 节保留旧名，因为那两节记录的正是**改名所依据的事实**。

---

## 0. 结论先行

1. **现有图标最大的问题不是"不好看"，而是"不像 OnlyRead"**——一本翻开的书是阅读器品类里被用尽的符号，无法回答"为什么不用别的阅读器"。真正值得画的差异化是产品那句"**打开单个文件，或直接打开整个文件夹**"，也就是左右分栏。
2. **但"语义最强"和"能站住"是两件事。** 我最初推荐把视觉锚点换成"分栏 + 文件树"，理由是它唯一能解释"为什么是 OnlyRead"。**实测推翻了这个推荐**：在 16px 下它糊成一个墨点（左侧方块只有 3.3px 宽，里面三根短划各约 1px），直接违反"16px 可辨认"这条硬约束。
3. **所以最终采用方向 A（双栏书）**：保留"书"的可读性，用两页向中缝折角收束。它只有 4 条笔画、剪影对称，是四个方向里**唯一**通过 16px 实测的。代价是它讲的是「阅读」而不是「OnlyRead 特有的左右分栏」——这个取舍明确记在这里，不用话术掩盖。
4. **一套形态语言**：标题栏/欢迎页的标记与应用图标**现在都是描边空心双栏书**（两页 + 中缝，不画书脊）。区别只在介质——标记是 24-viewBox 的 SVG、按 `size` 选描边；应用图标是逐像素光栅化的 PNG、按尺寸档选比例。

## 1. 现状诊断

### 1.1 资产盘点

| 资产 | 位置 | 现状 |
| --- | --- | --- |

| 字标 | `src/renderer/src/components/TitleBar.tsx` | 纯文本 `OnlyRead` |

| 品牌主色 | `src/renderer/src/styles/base.css` | `--accent: #2f7efc`，另有 `--accent-soft` 派生 |

### 1.2 应用图标：四轮迭代的实测过程

**(a) 起点问题：填充率偏低。**
`scripts/make-icon.py` 里书本多边形占画布 x 轴 12→88、y 轴 24→82，画布宽度 76% 但上下留白不对称，实际呈现偏小、偏轻。与相邻图标并排时会明显"缩一圈"。

**(b) 第一版：等比缩小 → 糊成一块。**
把大尺寸那套「页–缝–书脊–缝–页」结构等比缩到 16px：缝只剩 1.15px、书脊 1.54px，两条缝被抗锯齿抹成灰白糊边，**整枚图标退化成一块蓝白斑块，完全读不出"书"**。

**(c) 第二版：用背景当缝 → 仍是一个白块。**
改成"书脊不画、两页间露出背景蓝"。16px 实测缝只有 1.25px，而且它是"白色形状内部的一道蓝"、没有对比度，**看上去仍是一个白块**。同时暴露第二个问题：书宽 78% 时四个页角会从 22% 圆角处**戳出四个白色尖角**。

**(d) 第三版：实心档可用，但与预览页观感不符。**
小尺寸收到"书宽 74%、高 62%、实缝 14%"，页角不再越界，16px 可辨认。但交付后发现它与 `preview.html` 里展示的**描边空心**示意不一致。

**(e) 第四版（当前）：统一为描边空心。**
形态与 `ReaderMark` 同源，两档比例不同，原因见下。

| 尺寸档 | 几何 | 描边 | 中缝 |
| --- | --- | --- | --- |
| **≤ 32px** | 书宽 74%、高 62% | 书宽的 17%（16px 上 2.01px） | 书宽的 13.5%（1.60px） |
| **≥ 48px** | 书宽 74%、高 67.5%、带透视收束 | 书宽的 9.32%（512px 上 35.3px） | 书宽的 8.1%（30.7px） |

**为什么必须分档**：描边宽度 = 比例 × 边长。若全程用大尺寸的 9.32%，16px 上描边只剩 1.1px，会被抗锯齿抹成一圈灰线——这正是 (b) 踩过的坑。

**为什么不做插值**：两档是比例差异，中间态（缝半可见、描边半粗）恰好是最糊的形态，插值只会把最差观感搬到 33–47px 上。所以切换点直接定在 48px。

| 尺寸 | 实测外轮廓宽×高 | 描边 / 中缝 | 文件大小 |
| --- | --- | --- | --- |
| 512px | 74.1% × 67.4% | 17.66 / 30.69（视口单位） | 4 078 B |
| 256 / 128 / 64px | 74.1% × 67.4% | 17.66 / 8.83 / 4.41px | 2 145 / 1 504 / 1 203 B |
| 48px | 74.1% × 67.4% | 4.14px / 7.19px | 1 131 B |
| 32 / 24 / 16px | 74.1% × 61.9% | 2.57 / 1.93 / 1.29px | 1 036 / 1 016 / 976 B |

> 实心档没有删除。`make_icon.py` 里 `ICON_STYLE = 'stroke' | 'fill'` 可切换，两套几何常量都保留着。

### 1.3 一次交付事故与修正（值得记下来）

`preview.html` 里 5 张卡片的「应用图标 · 48 / 128 px」原本是**手画的 SVG 示意**——把标记的 24-viewBox 描边图形缩小塞进一个渐变 `<div>`，和实际交付的 PNG 不是同一个文件。结果"预览页看到的"与"最终交付的"对不上。

已修正：那 5 处已全部替换为真实 PNG（data-URI 内嵌），标签改为「应用图标（实际产物）」。对比留档在 `brand/preview-vs-actual.png`。

**教训**：评审页里凡是"示意"的东西都必须显式标注，否则它会被当成交付物本身。

### 1.4 ✅ 命名撞车（已实证，并且已按此改名）

这一节记录的是**改名的依据**，所以保留原名 `MetaReader`。

| 撞车对象 | 情况 | 风险 |
| --- | --- | --- |
| [元阅 MetaRead](https://apps.apple.com/cn/app/%E5%85%83%E9%98%85-metaread/id6766032127) | App Store 中国区**图书类**应用，iOS 小说阅读器，支持本地 TXT/EPUB | **高**：同品类 + 名称只差一个字母 |
| [MetaReader - Unofficial Client For MetaFilter](https://metareader-unofficial-client-metafilter.appstor.io/pt) | 已经叫 `MetaReader` 的应用 | **中**：占用同一英文名 |
| Meta Platforms（`Meta` 商标） | 在软件与应用分发类别有注册，且有实际维权记录（如 [Threads 名称争议](https://feddit.rocks/comment/1786797)） | **中**：取决于是否出海 |

**已执行的决定：改名为 `OnlyRead`。** 三条同名/近似名同时存在于同类品类，视觉上再怎么拉开距离也解决不了名称本身的问题，所以不再试图靠设计规避。

改名落地范围（全部已完成，`npm run typecheck` 通过）：

| 层面 | 变更 |
| --- | --- |
| 打包标识 | `package.json` `name: onlyread`；`electron-builder.yml` `appId: com.onlyread.app`、`productName: OnlyRead`、`executableName: OnlyRead` |
| 界面字串 | 窗口标题、标题栏字标、状态栏版本号、`index.html` `<title>` |
| 内部协议 | 流式读取协议 `mrfile:` → `orfile:`（含 `electron.vite.config.ts` 里 CSP 的 5 处白名单） |
| localStorage | 键前缀 `meta-reader.` → `onlyread.`，**但加了迁移**：老用户的主题、历史、收藏不会被清空 |
| 品牌资产 | favicon、应用图标脚本、图标验收表、预览页、`<svg>` 的 `title`/`aria-label` |

⚠️ 两点遗留影响：

1. **用户数据目录会变**：Electron 默认用 `name` 作为 `userData` 目录名，`meta-reader` → `onlyread` 会让旧目录被孤立。
   当前 version 仍是 `0.1.0`（未发布），所以实际影响可忽略；若已有真实用户，需要额外写迁移。
2. **`OnlyRead` 这个名字本身仍建议做一次检索**。已快速查过，未见同名软件产品；但它与 ONLYOFFICE 在"办公/文档"语境下读音接近，且 "read-only" 是通用术语，检索时要注意区分。

1.4 原有的第 3 条提醒仍然有效：⚠️ **「元读」不是安全的中文名**（既近似「元阅」，又对标 Meta 的官方中文名「元」）。中文名建议另起炉灶，避开「元」「Meta」「阅」的组合。

### 1.5 关于旧名里的 "meta" 前缀（为什么它不值得救）

这一节解释为什么"改名"比"在视觉上解释 meta"更划算，因此也保留原名。

`meta-` 在软件命名里通常是三种意思，其中**只有一种是能画出来的**，而且在小尺寸下最不可靠：

| 含义 | 例子 | 能否画出来 |
| --- | --- | --- |
| 元数据 / 关于自身的信息 | metadata, meta tag | 能，但靠"镜像、叠层、倒影"这类抽象手法，小尺寸下极易糊掉 |
| 跨越 / 更高一层的抽象 | metaverse, metaprogramming | 不能，画出来必然变成通用几何图形 |
| 自指 / 反身 | meta-joke, meta-design | 不能 |

而在旧名 `MetaReader` 下，这个前缀**根本无法承载视觉语义**：产品功能不涉及元数据，"跨越/自指"又画不出来。当时只有两条路——要么在 logo 里硬凑一个抽象镜像（方向 C，16px 下必然糊），要么放弃解释、只画"阅读"。

改用 `OnlyRead` 之后这个问题自然消失：**新名里没有可被误解的语素**，"Only" + "Read" 直白、无需视觉解释。这正是不该继续在 logo 里救 `meta` 的原因。

顺带一个对新名有利的点：`OnlyRead` 里的 "Read" 与标记的形态天然同构——**双栏书**同时读作"两页纸"和"左栏 + 右栏"，不需要任何附加说明。

## 2. 品牌定位（一切设计的判据）

从 `README.md` 与 `assets/images/refer.png` 提炼三条**可被视觉表达**的定位：

| 定位 | 依据 | 视觉翻译 |
| --- | --- | --- |
| **打开一个文件夹，就是打开一座书库** | "打开单个文件**或直接打开整个文件夹**" | 分栏：一栏是列表，一栏是内容 |
| **什么都能读** | TXT/代码、Markdown、HTML、PDF、Word、PowerPoint、图片 | 不绑定任何格式：不用 `{ }`、不用 `</>`、不用 PDF 折角 |
| **就地读取，不搬家不联网** | 本地文件系统、contextIsolation、无云端 | 冷静、精确、工具感；不要消费级电子书的暖色与拟物纹理 |

**一句话定位**：给开发者和文档工作者用的、能吞下任何格式的本地阅读工作台。

## 3. 四个设计方向与取舍

对比预览页：**`brand/preview.html`**（含 16/20/24/34/64px 尺寸阶梯、浅深双背景、应用图标实际产物、横向评分表）。矢量源文件在 `brand/logos/`。

### 方向 A · 双栏书 `concept-a-double-page.svg` ✅ 已采用

两页竖直折角，中间留一道窄缝。
- ✅ 16px 下依然读得出"书"；与现有 `ReaderMark` 语义连续，迁移成本最低
- ✅ 中间窄缝天然暗示"分栏"
- ❌ 仍在通用书本赛道里，差异化最弱
- **实测**：stroke 2.4 时 16px 最清楚；1.8 在 18px 偏细、在 34px 偏粗

### 方向 B · 文件树 + 内容面板 `concept-b-pane-tree.svg`

把真实界面抽象为图标：左边带缩进点的树，右边带文字行的内容面板。
- ✅ **唯一能回答"为什么是 OnlyRead"的方向**
- ❌ **16px 下糊成一个墨点**（左侧方块只有 3.3px 宽，三根短划各约 1px）
- **结论**：语义最强但违反硬约束，淘汰

### 方向 C · 实体页 + 元数据镜像 `concept-c-meta-ghost.svg`

前景实心描边页，后景一层虚线/半透明错位镜像。
- ✅ 唯一能表达 "meta" 字面含义的方向
- ❌ **16px 下基本失效**，两层糊成一团；作应用图标尚可，作标题栏标记不合格

### 方向 D · 折角页 + 书签 `concept-d-folded-corner.svg` / `d2` 变体

- ✅ 最安全、最通用，零学习成本
- ❌ 与 Apple Books、WPS、无数 PDF 工具撞车，几乎没有品牌资产价值
- **结论**：仅作对照组

## 4. 色彩规范

### 4.1 已有主色不要动

`--accent: #2f7efc` 已渗透到侧栏选中态、按钮、链接、拖拽虚线框等 19 处样式。换主色等于重做整个界面，收益远小于成本。**Logo 服从这个蓝，而不是反过来。**

### 4.2 语义色板

| 角色 | 值 | 用途 | 依据 |
| --- | --- | --- | --- |
| 品牌蓝 | `#2f7efc` | 主标记、强调、选中态 | 现有 `--accent` |
| 品牌蓝深 | `#1e4fd8` | 渐变暗端、深色底强调 | 同色相，不引入新色相 |
| 图标渐变 | `#2f7efc → #1e4fd8` | 应用图标底（左上→右下） | — |
| 图标前景 | `#ffffff` | 应用图标内的图形与描边 | 见 4.3 |
| 浅色底图形 | `#1f2328` | 浅色主题下的单色标记 | 现有 `--fg` |
| 深色底图形 | `#d6d8dc` | 深色主题/标题栏上的单色标记 | 现有 `--titlebar-fg` |

### 4.3 对比度（已逐项算过）

| 组合 | 对比度 | 结论 |
| --- | --- | --- |
| 白字 / `#2f7efc` | **3.80 : 1** | 仅够大字与图形，**不足以做小号正文** |
| 白字 / `#1e4fd8` | **6.43 : 1** | 通过 AA（正文） |
| 白字 / `#17181b` | **18.33 : 1** | 通过 AAA |
| `#1f2328` / `#ffffff` | 15.91 : 1 | 通过 AAA |
| `#d6d8dc` / `#26282c` | 11.31 : 1 | 通过 AAA |

两条可执行结论：

1. **应用图标（图形类）用 `#2f7efc → #1e4fd8` 渐变是安全的**——图形只需 3:1。但白色图形要落在渐变的中深区域，避免右上角过亮导致白色"化开"。
2. **不要把白色小号文字放在 `#2f7efc` 上**。现有 `.button--primary` 的白色文字在 14px 时对比度不足，属既有可访问性问题；顺手修的话把主按钮背景改用 `#1e5fd0`，或把文字升到 15px 以上。

## 5. 规格：尺寸阶梯与描边

描边图形**不能等比缩放**。同一份几何在不同尺寸下必须换描边粗细，否则要么发糊要么发胖。

### 5.1 标记（ReaderMark，24 viewBox）

| 尺寸 | 使用场景 | strokeWidth | 说明 |
| --- | --- | --- | --- |
| 16px | 小尺寸列表、任务栏缩略 | **2.4** | 已接近临界 |
| 18px | 标题栏（现状） | **2.0** | 当前值 1.8 偏细 |
| 24 / 34px | 欢迎页（现状 34） | **1.8** | 34px 时 1.8 已有约 2.55px，视觉重量与 18px 一致 |
| ≥ 512px | 应用图标 | 不用描边路径 | 改用逐像素光栅化，见 1.2 |

落地代码见 `brand/ReaderMark-替换补丁.md`（**未应用**）。

### 5.2 统一约束

- viewBox 恒为 `0 0 24 24`，图形安全区 `1.5 ≤ x,y ≤ 22.5`
- 组件层不写死 `width`/`height`，由调用方传 `size`
- 单色标记一律 `stroke="currentColor"`，**不要在标记里写死品牌蓝**——它必须在标题栏（深底）和欢迎页（浅底）上自动反色，这是现有 `ReaderMark` 做对的地方，务必保留
- 实心点用 `fill="currentColor"` 且 `stroke="none"`
- 应用图标内**不放任何文字**（缩放后必糊）。外边距：大尺寸约 12%（实测 11.9%–12.5%）；**小尺寸（≤32px）放宽到约 9%**，用边缘换可辨认度

## 6. 字标（Wordmark）

现状是纯文本 `OnlyRead`（`layout.css:35`）。两个层次的建议：

**A. 保持纯文本（推荐，成本为零）**
- 字重 **600**，`letter-spacing: -0.01em` 让拉丁字母更紧凑
- 可考虑只把 `Reader` 加到 **700** 做双色阶，用"功能词加重"点出产品核心，不需要引入字体文件
- 多平台渲染一致性由系统字体栈天然保证，零风险

**B. 定制字标（仅对外推广时值得做）**
- 必须导出为 **SVG 描边路径**，不要依赖 webfont——Electron 打包后字体加载失败会直接掉字
- 建议只定制首字母 `M`，让 `M` 的中间折线与标记的"分栏"结构呼应

## 附录：本文档的一次损坏与恢复

本文档曾被一次编码事故损坏：用 PowerShell 的 `Get-Content -Raw` + `Set-Content -Encoding UTF8` 批量替换时，PowerShell 按系统 ANSI 代码页（GBK）读取了 UTF-8 文件，导致中文整体变成乱码、且**部分换行被吃掉**（非法字节对被解码成 `?` 并同时吞掉两个字节，所以「中文尾字节 + `\n`」会让换行消失）。

四个文件受影响，处置方式不同：

| 文件 | 处置 | 结果 |
| --- | --- | --- |
| `设计建议.md` | 反向修复失败，重写 | 内容据此重写；损坏原文留档 `_check/设计建议.corrupted.md` |
| `README.md` | 重写 | — |
| `make_icon.py` | **从 `__pycache__` 的 .pyc 精确还原** | ✅ 编译对拍 26 个 code object 与完整行号表全一致；8 个 PNG 的 MD5 与损坏前完全相同 |
| `verify_icon.py` | 从 .pyc + 损坏文本还原 | ✅ 对当前 8 个产物报 0 error / 0 warning；7 类构造坏图均能报错 |

**两条可复用的经验：**

1. **反向修复不可靠。** `utf-8 → gbk → utf-8` 的往返在 `strict` 模式下会抛异常，说明有字节在误解码阶段就已丢失（非法字节对被解成 `?` 时是**有损**的，还会同时吞掉两个字节——这正是换行丢失的原因）。可用 `brand/tools/repair-encoding.py` 快速判定某个文件是"可修"还是"只能重写"：它对正常中文文件会正确跳过，对损坏文件会明确报 REPAIR FAILED。
2. **`__pycache__/*.pyc` 是被低估的恢复来源。** Python 编译产物保留了全部 docstring、常量、函数签名默认值，以及 `co_lines()`——**每条字节码对应的原始行号**。有了行号，注释块的行数就被唯一确定，还原从"凭记忆重写"变成"精确对拍"。所以：**源码被破坏时，先去看 `__pycache__` 的时间戳**，早于损坏时刻的 .pyc 就是干净的锚点。

### 附带修掉的一个校验器缺陷

重建 `verify_icon.py` 时顺带发现了它一个**逻辑写反**的检查：「圆角方块外必须透明」原本要求"邻居也在外侧"才判定，效果恰好相反——成片的不透明区域整片被跳过，只有孤立散点会被抓到。

实测证据（当时的构造脚本 `brand/_check/test-outside-guard.py`，已随 `_check/` 过程目录清理）：

| 构造的坏图 | 修正前 | 修正后 |
| --- | --- | --- |
| 真实产物 8 个 | 0 error | 0 error（无假阳性） |
| 整张画布涂满、无圆角无透明区 | **0 error（漏检）** | 1 error（69 个越界像素） |
| 圆角外撒 3×3 散点 ×4 角 | 1 error | 1 error（12 个像素） |

这条缺陷是**原设计就有的**，不是重建引入的；但"整张画布涂满"恰恰是最该被抓住的错误，所以已修正。

**教训（操作层面）**：在这个仓库里做批量文本替换时，不要用 `Get-Content`/`Set-Content` 往返处理含中文的 UTF-8 文件。要么用支持显式编码的工具（`-Encoding utf8` 在 Windows PowerShell 5.1 下也不等于 UTF-8 读取），要么直接用文件编辑工具。
